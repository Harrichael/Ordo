# Ordo — open issues

## Polling gaps (belief staleness up to one rescan interval, default 2s)

The architecture is "notifications are hints, scans are truth"; anything
without a hint is only as fresh as the periodic scan. Closed so far: external
focus changes (AXFocusedWindowChanged/AXApplicationActivated hints) and new
windows (AXWindowCreated). Still scan-only:

- External Space switches — MOSTLY CLOSED: a dedicated watcher thread polls
  just the SkyLight topology (one WindowServer read, no AX) every 150ms and
  hints the engine on change, so reaction is ~150ms instead of 2s. True push
  was probed and is unreachable from a daemon on Tahoe: AX has no space
  notification, NSWorkspaceActiveSpaceDidChangeNotification needs a real app
  identity (tried NSApplication init + main-runloop pumping; never delivered),
  and NO distributed notification fires on a switch (examples/notify_probe.rs
  listened to all of them). The zero-poll route is now CONFIRMED: private
  SLSRegisterConnectionNotifyProc events 1329/1401 fire on space changes —
  see the probed recipe under "Stacking research notes" (needs [NSApp run]).
- Window closes. Alt+Tab can target a window closed <2s ago; the focus op
  fails honestly and the next scan cleans up. Fix if it ever annoys: per-window
  AXUIElementDestroyed observers.
- Window moves/resizes. Only affects frame beliefs and monitor attribution
  (MruMonitor filter, move-to-other-monitor translation). Deliberately polled:
  move/resize hints fire in storms during drags and would need debouncing to be
  worth it.
- App launches. The AX observer attaches to new apps on a 3s timer, so hints
  from a freshly launched app can lag ~3s (its windows still appear via the
  periodic scan). Fix: NSWorkspace launch notifications on a pumped run loop.

## Native workspace switching — SOLVED via Mission Control's lever (notes)

Mechanism shipped in platform/mission_control.rs + NativeBackend: synthesize
the "Move left/right a space" shortcut, which the user rebound to
Ctrl+Alt+Cmd+arrows (to stay out of Hammerspoon's Ctrl+arrow bindings). Two
on-device facts make it work: the shortcut acts on the display UNDER THE
POINTER (so Ordo warps the pointer per display and restores it), and the
synthesized event needs a HIDSystemState source plus the exact stored flag
mask (Ctrl+Alt+Cmd + the secondary-fn bit arrows carry).

Graveyard, for the next macOS update (all probed on Tahoe 26.6, probes kept
in crates/ordo/examples/):
- Dock-swipe gesture synthesis (yabai/BTT trick): silently ignored.
- SLSManagedDisplaySetCurrentSpace: HALF-switches — SkyLight's record and AX
  visibility move, the compositor doesn't; focus hops, window scans go blind.
- + SLSShowSpaces/SLSHideSpaces: record moves, pixels still don't (these
  apparently drive the compositor only from inside the Dock, which is what
  yabai's SIP-off scripting addition is for).

Follow-ups:
- The lever chord is hardcoded; read it from com.apple.symbolichotkeys
  (parameters = [char, keycode, CGEventFlags-compatible mask]) so a user
  rebind can't silently break switching — and fail loudly at startup if the
  shortcut is disabled.
- Multi-step switches (e.g. ws 1 -> 5) are N animated presses ~350ms apart;
  if that grates, investigate "Switch to Desktop N" symbolic hotkeys
  (per-desktop direct jumps, need enabling + per-display probing).
- The pointer blips to each display's center mid-switch (restored after).
  Cosmetic; revisit if it bothers.

## New-window handling — reviewed 2026-08-27, oddities to pick from

Current behavior: the app's AXWindowCreated hint triggers a rescan; a new
window that TOOK FOCUS is corralled to the pre-existing focus context
(moved to the current workspace; translated to the focused monitor if it
opened on the other one). A window that opens without stealing focus is
left where the app put it. New windows enter MRU history at the back
unless focused. Michael flagged the area as "a little odd" but hasn't
named the symptom yet — candidates, ranked:

1. Fresh-app blind spot: the AX observer attaches to newly launched apps on
   a 3s timer, so the FIRST window of a just-launched app usually misses
   the created-hint — no corral, invisible to the model until the next
   periodic scan (up to 2s). Already-running apps get ~50ms handling; the
   inconsistency reads as flakiness. Fix: NSWorkspace launch notifications
   on a pumped run loop (also listed under polling gaps).
2. Cross-monitor teleport blink: an app that remembers its position opens
   on monitor B; if focus is on A, the window appears on B then jumps to A
   a beat later. Corral working as designed ("new windows come to you") —
   softening options: corral workspace-only (drop the monitor translate),
   or drop the corral entirely.
3. Non-focused new windows sink on the next switch: they sit at the MRU
   back, so a workspace round trip's restack buries them — "the window I
   just opened vanished". Consistent with MRU-is-stacking; if it grates,
   enter new windows mid-history (e.g. just below the focused window)
   instead of last.

## Smaller open items

- Dock dimming only re-evaluates at backend mutation points (switch / move /
  rescue). Gaps: an app that opens its first window on the visible workspace
  while hidden stays dimmed until the next switch, and a daemon that dies
  leaves apps hidden (rescue unhides everything; macOS also auto-unhides on
  activation, so Cmd+Tab is the manual escape). Fix if it grates: run the
  visibility pass from topology() — at the cost of a read having side effects.
- Focus-the-destination on switch doesn't warp the mouse: the core's frame
  belief for a parked window is its sliver position, so the warp would aim at
  the bottom-right corner. Fix: warp on the post-switch confirmation snapshot,
  once the restored frame is believed.
- The switch's stacking reassert is sequenced: each AXRaise is confirmed
  landed (CG read-back) before the next is issued — the only way cross-app
  ordering is deterministic, since apps apply raises on their own schedule
  and no WindowServer-side bulk ordering survives SIP (probed: SLSOrderWindow
  refused; SLPS bursts coalesce to the last call — slps_order_probe.rs).
  Since 2026-08-27 the reassert runs on a dedicated worker thread
  (platform/restack_worker.rs) with generation preemption: submitting is
  instant, a newer order cancels an in-flight one at the next 5ms gate tick,
  and the engine is never blocked by landing waits (it used to be deaf up to
  ~1.9s on a ghosted raise). Queued hotkey bursts are coalesced at dequeue
  (core's coalesce_hotkeys — clamp-walked fold into WorkspaceSwitchTo), so a
  rapid bounce annihilates instead of replaying stale. Two accepted residuals:
  a cancelled generation's in-flight raise can land during its successor
  (absorbed by the successor's second pass, same as any ghost), and a
  mid-handoff snapshot can transiently touch the wrong MRU head (focus
  follow-through is guarded by the pending Focused expectation; MRU-order
  pollution self-corrects on the next real focus). If stacking ever still
  feels slow, the lever is raising fewer windows (e.g. only the top K of
  the MRU) or the data-gated overlap plan below, not more threads.
  - Michael's overlap idea (2026-08-27, deliberately NOT implemented yet —
    full plan, physics, queries, and decision criteria in
    docs/raise-overlap.md):
    pipeline the raises optimistically — issue raise N+1 before N's landing
    is confirmed when per-app latency stats say it lands in order with
    p >= 99.9% — then detect misorder on the final read-back and fall back
    to the serialized pass (which already exists as the second/absorb pass).
    Same-app raises are FIFO in the app's AX queue, so those can ALWAYS
    overlap; only cross-app boundaries need the heuristic. Gated on data:
    the `restacks`/`raises` tables now log every reassert's phase breakdown
    (presence wait vs handoff wait vs per-raise landing wait, per pid, with
    burial depth) precisely so this can be designed from real distributions
    after a few weeks of use — including checking whether raise landings are
    even the dominant cost vs the presence wait.
- Stacking research notes (from alt-tab-macos / yabai / Hammerspoon source
  dive, 2026-08-27): no WindowServer-side reorder of foreign windows exists
  with SIP on — yabai injects into Dock for SLSTransactionOrderWindowGroup,
  alt-tab probed CGSOrderWindow ("does nothing"), Hammerspoon's sendToBack is
  focus-each + 80ms sleeps. Only windows OUR connection creates can be
  ordered relative to foreign ones (JankyBorders pattern) — the route to
  proxy-window switch animations if ever wanted.
- Zero-poll upgrade — PROBED, CONFIRMED, AND ADOPTED 2026-08-27 (examples/
  raise_notify_probe.rs, then platform/ws_events.rs; Tahoe 26.6): the
  WindowServer pushes per-window events, including for a PURE RAISE.
  Shipped shape: events are HINTS that wake a read-back, never the authority
  — every gate keeps a 50ms poll fallback (and its old timeout), so a deaf
  window or dead stream degrades to polling, never stalls. The reassert's
  presence/handoff/landing gates wake on 808/815 (raises.via_event logs the
  hit rate); the worker's post-convergence GHOST WATCH (1.8s, max 2 reruns,
  filtered to ordered windows) closes the "wrong until the 2s rescan" tail
  (restacks.ghost_pass, real ghost = ghost_pass row WITH raises); 1329/1401
  hint an instant rescan with the 150ms space watcher kept as backstop.
  main's thread now belongs to [NSApp run] (activation policy Prohibited);
  the periodic/shutdown loop moved to its own thread. Windows are opted in
  on the snapshot path (SubscribingWorld) — a window born between rescans is
  deaf until the next one, covered by the fallback. A background AXRaise of an onscreen
  window emits 808 + 815 carrying exactly that window id, instantly. So the
  reassert's landing gates (5ms CG-read polling), the trailing ghost-raise
  tail (a cancelled/timed-out raise landing after the final read-back — the
  "Outlook over the terminals until the rescan" symptom), and the 150ms space
  watcher can all go event-driven. The recipe, all three parts load-bearing:
  (1) SLSRegisterConnectionNotifyProc(cid, handler, code, NULL) per code;
  (2) SLSRequestNotificationsForWindows(cid, ids, n) — mandatory since
  Sequoia, and it REPLACES the connection's watch list (always send the full
  set; there is no unsubscribe symbol — dropping an id from the next call is
  the only removal); (3) a running NSApplication event loop ([NSApp run]) —
  the datagrams arrive via AppKit's connection event machinery, and a bare
  CFRunLoop gets NOTHING (measured: 0 events, identical registrations), nor
  does NSApplicationLoad() alone. yabai ends main with [NSApp run] for
  exactly this; adopting it in ordo means the main thread runs NSApp and the
  handler forwards to the engine channel. Confirmed code map (alt-tab's
  WsEventRouting + observed live): 811 created / 804 destroyed / 806 moved /
  807 resized / 808 focused-or-raised / 815 ordered-in / 816 ordered-out /
  1325-1326 space membership (payload: 8-byte space id + 4-byte wid; others
  carry just the wid) / 1329+1401 space change. Also seen, undecoded: 805
  (fires with membership flips), 1308/1322/1508 (activation/space-adjacent).
  Handler runs on AppKit's event thread — extract ints, hop threads, return.
- If Ordo ever drives native Spaces again:
  SLPSSetFrontProcessWithOptions clobbers other Spaces' front-process memory
  (alt-tab #4507, repair = SLSSpaceSetFrontPSN).
- Cross-monitor frame math targets the display's raw bounds, so macOS clamps
  the landing into the visible area (a menu-bar-height shift). Belief follows
  the clamp and the op confirms by monitor arrival, so nothing fights — the
  window just sits slightly off the proportional spot. Fix if it grates:
  plumb NSScreen.visibleFrame into MonitorSnap and translate within it.
- Follow-the-focus is unconditional: an app self-activating on a hidden
  workspace (Slack notification, Xcode build-done) yanks the user over, same
  as native Spaces does. If that annoys, add damping or an allowlist.
- Follow-the-focus snap-back under rapid switching — DIAGNOSED AND CAPPED
  2026-08-27 (run 38 seqs 1410/1451/1480/1491/1535, all FollowedFocus). The
  mechanism: a switch's FocusWindow grant lands (or DUPLICATES — kitty
  delivered the same activation twice, the second 520ms after the first) after
  the switch self-confirmed and the one-shot Focused expectation was consumed,
  so the arrival reads as external focus on a hidden-workspace window and
  follow-the-focus yanks back to the workspace just left. Event-driven hints
  made it worse: EXPECTATION_RESCANS=3 is now ~150-400ms of wall time, far
  under the measured ~1.6s app landing tail. No observation channel can fix
  this — the OS doesn't say WHO caused a focus change; only our own recent-op
  memory can.
  Shipped fix (blunt on purpose): FOCUS_SETTLE_NS in update.rs — within 2s of
  any SwitchWorkspace we emitted, a stray focus onto a hidden workspace is
  treated like close fallout (hold the workspace, pull focus back to the
  current MRU head; note held_focus_settling). Cost: a genuine Cmd+Tab to a
  hidden-workspace window within 2s of a switch gets bounced back once —
  accepted, same trade as HeldFocusOnClose ("a wrong yank costs far more").
  Sharper options if the lost-follow ever grates (deliberately not built):
  (a) per-window fallout horizon — remember each window we granted focus in
      the last 2s and only suppress follows onto THOSE, with per-entry early
      expiry once the grant confirmed AND stayed quiet ~300ms; genuine
      Cmd+Tab to any other window follows instantly even mid-burst. Strictly
      better; slightly more state.
  (b) quiet-based early exit on the blanket window (close at 300ms of focus
      quiet) — simpler than (a) but re-opens before kitty's sparse tail and
      turns the quiet threshold into a forever-tuning knob. Prefer (a).
  Strict "all expected events accounted for → expire early" is UNSOUND: the
  trace above had every expected event accounted for at t=384 and the
  snap-back still arrived at t=522 as a duplicate. Fallout has no complete
  ledger. Same lesson feeds the reconciler plan (finding 15 there): an
  in-flight set that dies at generation end can't classify landed-then-
  superseded grants either.
- PHANTOM WINDOWS — diagnosed 2026-08-28 (run 38 seqs 20599-20682), band-aid
  shipped same day. Mechanism: park/restore frame writes have the same
  apply-on-the-app's-schedule AX physics as raises but NONE of the raise
  machinery (no landing gates, no generation preemption, no ghost watch).
  Rapid ws bouncing puts a park and the PREVIOUS switch's restore in flight
  for the same window; log caught a restore landing 600ms AFTER the park that
  superseded it. Last-lander-wins → window visibly on-screen, ledger says
  parked. No delta ever fires again (reconcile is delta-driven; a settled
  phantom is a standing violation), so it persisted until the next clean
  round-trip. Downstream symptoms, all corrupted-belief, not bad rules:
  clicking a phantom follow-the-focuses you to its believed workspace; MRU
  filters (Alt+Tab/backtick/shift-tab) leak across workspaces/monitors —
  window `monitor` is derived from frame center and flips displays through
  the park corner on every transit.
  Band-aid (this commit): WorkspaceBackend::enforce_placement — a standing
  check per rescan, emulated impl re-parks any believed-parked window not at
  its sliver, damped at 3 per window (mirrors core damping), reset when it
  parks clean or unparks; gated on the intercepting flag so a paused/rescued
  daemon never fights a rescue gather. The re-park write lands post-snapshot
  and is absorbed as an External delta next rescan — attribution honesty is
  deliberately sacrificed; this dies at reconciler R3 when plan() owns
  park/restore and the phantom becomes just another goal-vs-belief diff.
  REAL FIX: the reconciler (docs/desired-state-reconciler.md) — the fifth and
  sixth members of the staleness class (carry mis-target via lagging believed
  focus; phantom via unowned frame writes) both land in its R1-R5 scope, and
  the phantom one is NOT cheaply fixable under the current model. Michael has
  agreed to review the rearchitecture plan next (2026-08-28).
- WEEKEND AMNESIA + PERSISTENCE — diagnosed and fixed 2026-08-31. Over a
  sleeping weekend, displays vanished and AX scans came back empty; the
  daemon read that as "every window closed": ledger.forget_missing erased all
  assignments, and Monday's wake re-adopted all 12 windows onto the current
  workspace (ws3). Worse, the backend's parked/saved maps were NOT forgotten
  in lockstep, so the phantom band-aid spent the morning re-slivering windows
  the ledger had re-adopted (1,526 fight lines). Three fixes:
  (a) An empty observation is not an observation of emptiness — engine drops
      snapshots with zero monitors; the emulated backend skips forget/adopt
      on an empty window list. (Reconciler doc: this belongs in the snapshot
      contract. Hardening deferred: forgetting still fires on a single
      partial scan; N-consecutive-absences would close that.)
  (b) parked/saved/enforce_attempts prune in lockstep with the ledger.
  (c) enforce_placement never parks a window assigned to the current ws —
      the ledger outranks the parked set.
  PERSISTENCE (statefile.rs): ledger promises (assignments, parked restore
  frames, current ws) write through to state.json next to the log DB and
  reload on boot — F6b is fixed; restarts are placement-invisible. Trust
  model: kern.boottime seal voids the file across reboots (CGWindowIDs
  regenerate), out-of-range entries dropped, missing windows pruned by the
  first sighted scan, `ordo run --fresh` ignores it entirely. First lossless
  restart: run 40, seeded from the log DB. At reconciler R3 this file's
  contents become Desired's placement slice — schema is data, not backend
  internals. Deferred: rescue does not tombstone the file (post-rescue state
  mirrors the gathered reality, and --fresh covers the rest); MRU history is
  not persisted (Alt+Tab starts cold after restart).

- Carry-to-workspace (Ctrl+Cmd+arrows) briefly blinks the carried window on the
  emulated backend: the move parks it (one AX write) and the switch restores it
  (another), because they're two independent backend calls. Fix if it grates:
  teach the emulated backend to coalesce a park+restore of the same window
  within one effect batch, or add a combined move-and-switch backend op.
- Native-backend switches are inherently per-display sequential: the Mission
  Control lever targets the display under the pointer, so displays must be
  driven one at a time and each plays its own animation. The emulated backend
  (now batched + parallel per app) is the sync answer; no known native fix.

- Alt+Tab is a strict two-window toggle (most-recent excluding current).
  Michael wants Alt+arrows to CYCLE the MRU list — deliberately deferred
  ("let's wait on the alt arrows thing"). Design questions when picked up:
  does cycling commit focus at each step or only on release (release needs
  key-up tracking in the tap), and does a cycle re-order history or peek it?
- Emulated-mode switch animation (asked 2026-08-27): possible, two routes.
  (a) Step AX SetWindowFrame along a path — works but sync-IPC per frame per
  window; janky beyond a few windows, Electron apps worst. (b) Compositor-side
  slide via private SLSSetWindowTransform (what yabai's --animate uses):
  smooth and cheap, another SkyLight adventure to probe. Park until the
  instant switch has been lived with — animation may not be missed.
- Focus/write latency: every AX write re-finds its window by enumerating all
  apps (deliberate no-stale-handles policy). If focus feels slow now that the
  logic is right, the fix is the AXUIElement registry cache from the original
  plan.
- fold_topology is not spans-mode-aware: with "Displays have separate Spaces"
  OFF, the single managed display resolves only to the main monitor and the
  others fall back to workspace 1 (harmless: damped tear realign + log noise).
  ~10-line fix in fold_topology if we ever want to support spans mode.
- Deferred review findings F5/F6b/F7/F9/F10 — see the review-fix plan notes in
  git history (fa426ca) for rationale; F6b (persist the emulated ledger across
  restarts) matters if the emulated backend becomes the daily driver.
  F6b BIT TWICE ON 2026-08-27, now understood precisely: restarting the
  daemon while any workspace is hidden strands that workspace's windows as
  1px corner slivers, silently. Mechanism: the fresh ledger has no `saved`
  entry for an already-parked window, so the next switch's restore() emits
  NO write (Option chain returns None), the window stays at the corner, the
  rescan adopts corner-as-truth (belief follows reality), and the next park
  saves the corner as its "real" frame — ossified, no error anywhere.
  Recovery (proven live, no daemon restart): while the window's workspace is
  CURRENT, externally move it to a sane frame — the rescan adopts it and the
  next park inherits it. Moving it while parked gets reverted by design.
  Fix when picked up: persist saved+parked (XDG state or the log DB), plus a
  startup sanity pass — any window sitting at the park corner with no ledger
  entry gets a cascaded onscreen frame instead of being adopted as-is.
